## 1. 概述

### 1.1 做什么

把来源混乱的 TXT 小说整理成结构化数据：

- **输入**：一个或多个 TXT 文件（UTF-8 / GBK / Big5 等，可能含 HTML 残留、乱码、硬换行、站点广告）。
- **输出**：结构化书本数据库（书籍 / 卷 / 章节 / 段落结构）与重新导出的干净 TXT。

Retree 不承担文学编辑或内容创作，只负责恢复原本的结构、修复格式损坏、识别非正文内容。

### 1.2 设计目标

- **原文保真**：正文文字来自原文块，不经模型改写。
- **实现简单**：单进程、单条流水线、少量模块。不引入多模型、不训练模型、不做调度框架。
- **可追溯**：每段正文都能追溯到原文块与偏移；每次删除都有记录和理由。
- **可恢复**：支持中断续跑；处理失败的块原样保留，不影响其他块。

### 1.3 非目标（明确不做）

- 小说润色、文学改写、情节补全、人物关系与世界观分析。
- 全量自动订正错别字（只提示，默认不改语义）。
- 联网搜索补全缺失章节；直接修改或覆盖原始 TXT 文件。
- 多用户、权限体系、Web 审核界面、任务队列、监控看板。

### 1.4 单人项目的取舍原则

- 只有本人使用，所以不需要向后兼容的复杂协议、不需要插件化、不需要多套配置隔离。
- 能靠"重跑一遍"解决的问题，就不写复杂的增量逻辑；缓存只用来省时间和 token。
- 每加一层抽象都必须立刻用得上；用不上的写进 [14. 暂不实现](#14-暂不实现)。
- 早期目标是"先把一个完整流程跑通"，不是"把将来可能用到的东西提前搭好"。

## 2. 技术路线

### 2.1 核心思路

1. 程序负责编码、HTML 实体、繁简转换等确定性处理。
2. LLM 批量分析所有文本块，判断结构类型、异常内容和段落边界。
3. **正常文本直接保留原文，不由 LLM 重新生成。**
4. 只有存在问题的文本，才由 LLM 输出局部修复结果或操作指令。
5. 程序负责应用修复、结构组装、来源追踪、差异校验和断点续跑。
6. 保留原有的广告识别、章节识别、跨分片处理及人工复核机制。

### 2.2 流水线

```text
原始 TXT
  │
  ▼
[1] 解析            编码检测与解码，保留原始字节与哈希
  │
  ▼
[2] 规则预处理      换行/空白/HTML 实体/控制字符/繁简转换，切分文本块
  │
  ▼
[3] LLM 全量判断    每个文本块 → 结构类型 + 异常标记 + 段落边界动作
  │
  ▼
[4] 按需局部修复    只对 [3] 标记为有问题的块发起，返回局部替换或操作指令
  │
  ▼
[5] 校验与组装      来源覆盖、差异对齐、删除审计、跨分片拼接
  │
  ▼
[6] 导出            结构化书本数据库 / TXT / 处理日志
```

[1] 与 [2] 不依赖 LLM，可以单独跑通并有可用产出；从 [3] 开始才需要模型（思路 1）。

### 2.3 关键设计：LLM 只判断，不产出正文

保住原文靠协议强制，而不是靠提示词叮嘱：

- 判断阶段的响应 schema **不存在文本字段**，模型只能返回 `keep`、标签和边界动作。
- 需要保留的块，正文由程序用 `block_id` 从原文块**直接拷贝**。
- 只有被标记为有问题的块才进入修复阶段，且只允许在程序给定的字符范围内替换。
- 校验不通过 → 该块回退为"保留原文 + `needs_review`"，其余块不受影响。

### 2.4 为什么不用 FastText / MacBERT / pycorrector / 自训练分类器

个人项目的样本量和运维精力都不支持：

- 模型加载、版本、权重、阈值、标注集、训练流程是一整套额外工程。
- 单一模型只覆盖单一任务，还要再串起来，覆盖面反而不如一次 LLM 判断。
- 真正增加的负担是 token 成本，而个人日处理量配合批次聚合与缓存完全可接受。

结论：**规则负责确定性判断，其余全部交给 LLM。**

## 3. 处理流程

### 3.1 解析

- 编码：UTF-8/BOM、GBK/GB18030、UTF-16 LE/BE、Big5 等；用 `charset-normalizer` 检测，并用实际解码质量验证（非法字符、替换字符、中文占比）。
- 编码无法可靠确定时记录问题，**不得通过忽略解码错误静默丢弃字节**。
- 保存原始字节与其哈希，供恢复与校验。
- 统一内部换行表示，去 BOM；同时记录原始换行、缩进与空行信息（缩进和空行在小说中可能具有结构意义，不能在分析前不可逆地全部删除）。

### 3.2 规则预处理

确定性处理，顺序固定：

1. 去 BOM，识别并处理无意义控制字符。
2. HTML 实体还原（`&nbsp;`、`&amp;` 等）；`<br>` 作为换行候选，`<p>` / `<div>` 作为段落边界候选，逐条记录。不用正则一刀切删除尖括号内容——小说里可能出现代码、聊天记录、系统面板等有意保留的 HTML 文本。
3. 规范化明确的异常空白。
4. 繁简转换（OpenCC，允许关闭），保留转换记录，支持专有名词例外词典。
5. 切分为**文本块**：以原始行为最小单位，生成稳定 ID 与偏移。

### 3.3 LLM 全量判断

- **输入**：全部文本块（按批次组织，带稳定 ID），必要时附相邻块以及当前书籍/卷/章节状态。
- **输出**（每块一条）：
  - `role`：结构类型。
  - `issues`：异常标记。
  - `boundary`：与下一块的 `merge` / `keep` / `uncertain`。
- **结构类型**：`book_title`、`author`、`volume_title`、`chapter_title`、`section_title`、`toc`、`body`、`author_note`、`noise`、`unknown`。
- **异常标记**：乱码、HTML 残留、异常空白、拼音混用、疑似错字、异常标点、重复片段。
- 规则先跑一遍给出**提示**（章节正则命中、疑似广告模板命中等）并塞进 prompt，但结论由 LLM 给出；思路 1 所指的确定性格式问题不进 LLM，直接由程序修复。

协议细节见 [4. LLM 协议](#4-llm-协议)。

### 3.4 按需局部修复

只对判断阶段标记了 `issues` 的块发起，见 [4.2 局部修复](#42-局部修复)。

### 3.5 校验与组装

- **来源覆盖**：每个正文块必须被某个事件引用，采用字符级对齐（见 [5.4](#54-覆盖校验)）。
- **差异校验**：事件文本与原文块按 `精确匹配 → 空白换行归一 → 繁简归一 → 字符级差异对齐` 的顺序尝试；无法对齐的内容增删全部进入异常报告。
- **删除审计**：任何删除都必须带 `reason` 与来源块 ID。
- **跨分片聚合**：跨分片段落由组装器拼接，单个分片不得复制其上下文中的文本。

### 3.6 导出

结构化书本数据库 + 干净 TXT（保持原文顺序，目录、附言、番外等区段不丢失）+ 处理日志。

## 4. LLM 协议

### 4.1 判断批次

请求：

```json
{
  "task": "block_judgement",
  "batch_id": "c0007",
  "context": {"book": "某书", "volume": null, "chapter": "第三章"},
  "hints": [{"id": "b00121", "rule": "chapter_pattern"}],
  "blocks": [
    {"id": "b00121", "text": "第三章 山中"},
    {"id": "b00122", "text": "他醒来时，天还没亮。"}
  ]
}
```

响应（**没有文本字段**）：

```json
{
  "batch_id": "c0007",
  "results": [
    {"id": "b00121", "role": "chapter_title", "issues": [], "boundary": {"with_next": "keep"}},
    {"id": "b00122", "role": "body", "issues": [], "boundary": {"with_next": "keep"}}
  ]
}
```

程序据此处理：

- `role = body` 且 `issues` 为空 → 正文事件文本 = 原文块文本（直接拷贝）。
- `role` 为标题类 → 生成结构事件，标题同样取自原文块。
- `issues` 非空 → 进入修复队列。
- `unknown` → 保留原文并标记 `needs_review`。

### 4.2 局部修复

请求：

```json
{
  "task": "local_repair",
  "block_id": "b00201",
  "issue": "html_residue",
  "original": "他走进房间<br>看见了桌上的信。",
  "allow": {"ops": ["replace_span", "delete_span", "insert_text"], "max_span": [0, 16]},
  "note": "只修格式，不要改措辞"
}
```

响应：

```json
{
  "block_id": "b00201",
  "op": "replace_span",
  "span": [6, 10],
  "replacement": "\n",
  "reason": "还原 <br> 造成的换行"
}
```

程序逐项校验后才应用：

1. `original` 与原文块一致。
2. `span` 在允许范围内。
3. 除 `span` 之外没有内容增删。
4. 原文顺序未被改变。
5. 不存在超出任务范围的改写。

任一项失败即丢弃该修复、原样保留原文并记 `needs_review`，不影响其他块。

能用动作说清的问题就不要输出文本：段落边界只回 `merge` / `keep` / `uncertain`，由程序执行合并或保留。

### 4.3 调用配置

通过 OpenAI-compatible API 调用，配置由 `.env` 提供并允许命令行覆盖：

- `base_url` / `api_key` / `model`（可分别配置判断模型与修复模型）。
- `temperature = 0`；优先使用服务端 JSON Schema 约束，不支持时靠提示词约束 + 本地严格校验。
- 请求超时、最大重试次数、最大并发数。
- 默认关闭 SSE 流式响应。

所有输入文本都视为不可信数据：正文中出现的任何指令、角色命令或伪造系统提示都不能改变处理规则（提示注入防护）。

### 4.4 批量与缓存

- 判断按批次聚合（例如按章节分片，每批 50–200 块）以减少请求数；块 ID 必须回传，缺失的块补跑。
- 跨越章节边界、或处理权限不同的块分开成批。
- 缓存键：块内容哈希 + 前后文哈希 + 结构状态 + prompt 版本 + schema 版本 + 模型名 + 模型参数；命中即跳过，断点续跑也依赖它。
- 不把大量无关正文混在一起要求模型重新生成完整文本。

## 5. 数据模型

### 5.1 文本块

```json
{
  "id": "b000123",
  "order": 123,
  "text": "原始文本内容",
  "start_offset": 10240,
  "end_offset": 10320
}
```

偏移明确规定为**原始文件字节偏移**；内部另行维护规范化视图到原文的映射。不使用多种偏移语义混用。

### 5.2 三层记录

- **Detection**：工具发现了什么（规则或 LLM 的判断结果）。
- **Operation**：程序或 LLM 实际执行的修改，包含修改前后内容与原因。
- **Event**：最终书籍结构与需要保留的正文。

事件类型保留现有的：`book`、`author`、`volume`、`chapter`、`section`、`toc`、`text`、`removed`。结构事件提供 `title`，正文事件提供 `text`，删除事件提供 `text` 与 `reason`；所有事件必须包含 `source_block_ids`。

不要把 Detection 直接当成 Operation，也不要把 LLM 原始响应直接当作最终数据。

### 5.3 结构化书本数据库

```text
Library
 └─ Book
     ├─ Metadata
     ├─ Volume            （可选，没有分卷就不生成虚构卷标题）
     │   └─ Chapter → Paragraphs
     └─ Section → Paragraphs
```

保留原文顺序索引，保证目录、附言、番外等区段按原始顺序导出。书籍标题缺失时可以使用程序生成的显示名，但必须标记为非原文标题。

### 5.4 覆盖校验

仅检查每个块"至少被引用一次"不够——一个块可能被部分引用而丢失了其中一句话。因此按以下顺序尝试字符级对齐：

1. 原文精确匹配。
2. 空白与换行归一化匹配。
3. 繁简归一化匹配。
4. 字符级差异对齐。
5. 无法可靠对齐时标记异常。

对齐关系由程序计算，不让 LLM 生成字符偏移。所有无法归类为已记录操作的内容删除与替换都进入异常报告。

### 5.5 跨分片

分片优先级：明确章节边界 > 明确自然段边界 > 空行 > 普通换行 > 强制切片。

每个分片带：自有原文块、前文参考、后文参考、当前结构状态、边界状态。**前后文只能用于辅助判断，不能成为输出内容的来源。** 跨分片自然段由组装器恢复；跨分片章节与书籍状态由统一结构解析器维护，避免不同分片重复创建同一章节或书籍。

## 6. 保留的机制

### 6.1 广告与站点噪音识别

三级处理：

1. **规则**：命中已知固定模板、域名推广格式、下载器标记、常见导航信息。
2. **LLM 上下文判断**：聊天里发网址、虚构世界中的广告、系统流小说的界面文本、作者求票感言都可能含推广词，不能仅凭关键词删除。
3. **人工复核**：LLM 仍不确定或涉及删除时进入复核。

结论分三档：**明确噪音**（生成排除建议，原文始终保留在审计数据中）、**疑似噪音**（不得直接删除）、**正常内容**。作者附言默认保留。整体原则是优先避免误删正文，而不是追求广告召回率。

### 6.2 章节与卷识别

正则先给出候选，例如 `第一章`、`第一百二十三章`、`第三卷`、`卷二`、`Chapter 12`、`序章`、`楔子`、`尾声`、`番外`、`上架感言`；规则只生成候选，最终分类由 LLM 判定并结合结构一致性分析：

- 连续出现大量章节标题，可能是目录而非多个真实章节。
- 章节编号重置不必然意味着新书开始。
- 不要求所有小说使用固定编号体系。

跨分片的章节与书籍状态由统一结构解析器维护。

### 6.3 人工复核

早期不写图形化审核界面，只维护一份待审清单（`needs_review.json` 或 SQLite 一张表），包含：待审块、原文、程序或 LLM 的建议、理由。

处理方式：人工查看后修改配置或添加例外词典，重跑该分片。人工确认的结果单独保存，不被后续自动流程覆盖。

## 7. 状态与缓存

### 7.1 状态

每个处理单元记录状态：`pending`、`running`、`completed`、`needs_review`、`failed`。

`completed` 表示该单元已通过必要的结构与内容校验；`needs_review` 表示结果可以保留，但仍存在未解决的风险或歧义。

### 7.2 缓存

按处理阶段分离缓存：解码结果、规范化文本、判断结果、修复结果、结构组装结果。各阶段使用独立失效条件，避免改了 prompt 之后重跑那些不需要重跑的确定性步骤。

### 7.3 失败与重试

出现以下情况应标记失败或进入复核：API 失败或拒绝、响应被截断、JSON 格式错误、输出不符合 Schema、引用了不存在的原文块、来源范围无法验证、发生未解释的内容删除、事件顺序异常、结构组装冲突。

技术性错误可有限重试；内容逻辑错误不能靠"反复调用直到某次返回看起来合法"。

## 8. 安全约束

以下约束不可破坏：

1. 原始文件永不覆盖。
2. 所有原文内容必须可追踪；内容删除必须有明确记录与理由。
3. 原文顺序不得擅自改变；正文不得被模型自由润色。
4. **正文文本只能来自原文块，不得由模型生成。**
5. 无法判断的内容默认保留。
6. 任意修改都应能够撤销（保存修改前后内容即可回滚）。
7. 校验失败不能静默视为成功。

## 9. 配置

### 9.1 基础配置

输入文件路径、输出目录、是否转换繁体为简体、是否启用 LLM、是否处理疑似广告、清洗策略。

### 9.2 清洗策略预设

- **Conservative（保守）**：只执行明确的格式修复；疑似广告、错字与复杂结构一律保留或记录待复核。
- **Standard（标准，默认）**：执行完整 LLM 判断，自动处理经过验证的低风险问题，复杂问题按需局部修复。
- **Deep（深入）**：提高检测覆盖度与修复允许度，但仍禁止无依据的改写与删除。

三种模式共享同一套核心规则和安全约束，区别只在检测灵敏度、自动处理阈值和 LLM 使用范围。

### 9.3 高级配置

模型名称、并发与批次参数、超时与重试、缓存开关、输出格式。

重要的参数由统一的配置对象管理，并随处理结果一起记录，保证结果可复现。

## 10. 技术选型

Retree 使用 Python 实现（与 Glean 现有技术栈一致）。

| 用途 | 选型 |
|---|---|
| 编码检测 | charset-normalizer |
| HTML 处理 | 标准库 `html.parser` / `html` |
| 繁简转换 | OpenCC |
| 正则与结构规则 | `re` |
| 文本对齐与差异 | difflib |
| JSON 校验 | Pydantic |
| LLM 调用 | OpenAI-compatible HTTP 客户端 |
| 状态与缓存 | SQLite |
| 输出 | JSON、TXT |

不引入 NLP 模型框架、不训练模型、不上向量库。上表是使用到的库，而非需要一次性全部安装的依赖清单。

## 11. 模块划分

```text
retree/
├── parser/      encoding.py  blocks.py  rules.py
├── llm/         client.py  prompts.py  schemas.py
├── pipeline/    judge.py  repair.py  validate.py
├── structure/   events.py  assembler.py
├── storage/     state.py  cache.py
├── export/      json.py  txt.py
├── config.py
└── cli.py
```

职责边界：

- `parser` 只做确定性处理，不调用模型。
- `llm` 只负责发请求、收结构化结果，不做业务决策。
- `pipeline` 决定做什么，并把结果落成 Operation。
- `structure` 负责最终数据组装。

模块之间只通过数据模型交互。目录划分可随 Glean 现有结构微调，不追求一次到位。

## 12. 实施计划

**Phase 1 — 跑通不依赖 LLM 的部分**
编码检测、文本块与来源追踪、规则预处理（空白 / HTML / 繁简）、规则式章节识别、结构化书本数据库组装与 TXT 导出、缓存与断点续跑、基础差异校验。

**Phase 2 — 接入 LLM 全量判断**
判断协议与 JSON Schema、批次组织与缓存、结构类型 / 异常 / 段落边界判定、来源覆盖校验。

**Phase 3 — 按需局部修复与复核闭环**
修复协议与校验、广告三档策略、`needs_review` 流程、错误恢复与重试。

每个阶段结束时都应能用真实小说完整跑一遍；不提前实现后续阶段的东西。

## 13. 验收

早期验收标准是"跑得通、不丢字"，而不是准确率数字。至少要覆盖：

- UTF-8 / GB18030 / Big5 等编码。
- 含大量 HTML 标签的小说。
- 固定行宽硬换行、无空行分段。
- 对话、诗歌及特殊排版。
- 章节编号不连续、卷标题与章节标题混合、目录与正文标题重复。
- 多本小说拼接、广告与作者附言混合。
- 拼音混用与明显错字。
- 长篇小说的跨分片章节。
- API 出错、拒绝与响应截断。
- 处理中断后的恢复。

判据：

1. 不静默丢失正文。
2. 常见章节能够正确识别。
3. 明显格式问题能够稳定修复。
4. **正文重写率为 0**（没有一段正文由模型生成）。
5. 不确定的内容能够保留并报告出来。
6. 处理失败能够恢复。
7. 导出结果保持文本顺序与内容完整性。

具体的准确率与性能目标在积累真实测试样本后再确定，不预先设定缺乏实测依据的数字。

## 14. 暂不实现

以下内容明确推迟，避免架构在早期变得复杂：

- 任何传统 NLP 模型（FastText / MacBERT / pycorrector / 自训练分类器）以及配套的标注、训练、评测流程。
- 指标看板、质量报告系统、CI 评估流水线。
- 图形化审核界面、多人协作、权限体系。
- 插件化检测器框架、模型热插拔、特征平台。
- 多模型投票与冲突仲裁框架（当前只有"规则 + LLM + 程序校验"三方，冲突用少量手写规则处理即可）。
- 分布式、任务队列或并发调度框架；单机 `asyncio` 足够。
- 增量 diff 更新与配置文件版本迁移。

需要时再加，不加也能用。

## 15. 一句话总结

**能确定性解决的不用模型；LLM 只判断、不改写；正常文本原样保留；只有出问题的文本才局部修复；最终数据一律由程序组装。**
